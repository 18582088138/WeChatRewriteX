# NUC 部署复验分析与下一轮完成条件

依据 `dev/v1-plus` 的 `beed771`、`10bcd44` 及[家庭复验记录](home-validation-2026-10-31.md)。本轮在公司开发机分析、修改工具和隔离补测，没有连接或配置 NUC，也没有操作真实数据。

## 为什么没有完成全部验证

现有证据更支持“验证范围和交接流程没有闭环”，不支持已经发生硬件性能不足或 Agent 能力不足。

- NUC8i5BEH 为 i5-8259U（4核8线程）、31.9GB内存；检查时空闲内存约16.7GB、C盘可用32.1GB。120项后端98.60秒、7+3浏览器和Windows完整团队流程通过，报告没有OOM、资源耗尽或无法完成任务的记录。
- 20项目并行读P95为58.73ms，但属于进程内固定集。它不能证明真实HTTP、持续渲染、真实模型、Wi-Fi/跨网络和长期热负载表现。公司机与NUC的测试环境不同，测试耗时不能直接作为硬件跑分。
- 用户补充：给部署机Agent的任务是依据dev/v1-plus文档和进展测试，没有额外要求它持续完成全部真实部署。报告明确按代表性复验结束，并把正式安装和剩余组合测试交接出去。
- 原记录先将NUC识别为普通开发机，后续才确认它就是部署机。确认设备后，安装、自启动和权限等本机工作仍未实施，说明任务范围没有重新闭合；部分“等另一台主机”的文字也没有同步更新。
- 本机可以继续做的角色/API组合、UI路径和故障补测，与需真实条件的外地成员、手机/蜂窝、另一设备备份、3～7天试运行被一起留待后续。后者确实不能由本机自动化代替，前者可以继续推进。

没有模型信息、工具拒绝记录、重复失败后的尝试轨迹或资源监控，不能比较Agent能力或认定它无法执行剩余任务。初次wheel命令相对路径错误已修正并通过，属于执行错误，不是机器故障或能力测评结果。
“按现有文档复验”可以得到代表性通过；“持续完成正式部署及所有可执行验收”需要明确结束条件。指令清晰度影响完成范围，不是增加硬件性能。

## 本轮修正与证据

- Windows离线备份脚本新增 `-ExecutablePath`，绿色包部署不再被脚本要求安装Python；原 `-PythonPath` 路线保留。停止运行中的计划任务后等待状态退出，再调用有OS数据根锁保护的离线备份；成功或失败后恢复原先运行的任务。
- PowerShell模拟任务测试8项通过（12.08秒），覆盖两种CLI、原先运行/停止与CLI成功/失败。模拟测试不证明NUC计划任务实际可注册或可开机运行。
- 新增HTTP矩阵：3成员等级 × 6项目关系（无授权/只读/创作/审核/两者/负责人）× 2归档状态，共36种组合；覆盖13类代表性项目/文件请求及系统管理、初始改密/退出会话边界。未获准修改时同时核对revision未改变。
- 团队测试、部署回归和脚本测试合计28项通过（84.90秒，无跳过）。这是本轮相关验证，不是把28项加到历史120项后宣称全量重新跑过。
- 新增 `scripts/windows_deployment_probe.ps1`，只读记录机器、内存/CPU瞬时值、runtime所在盘、计划任务、睡眠策略和本机公开health/auth状态。公司机实跑通过，明确识别了不存在的测试任务与未启动端口，没有安装服务或创建runtime。
- 产品业务代码、版本和schema未改变；没有复现部署报告中的产品缺陷。原候选标签/安装包不覆盖，本轮新增脚本从更新后的Git工作区使用。既有exe不会自动获得新增外置脚本。

## NUC 的部署与验收顺序

### 1. 收集基线并保护真实数据

先核对NUC工作区是否有本机改动，获取最新dev/v1-plus；确认当前使用的exe、`--version`、`--build-info`和其SHA256清单。不同机器重新构建的同版本ZIP可能有不同SHA，按该构建自身清单校验，不拿公司机ZIP的SHA要求NUC重构建包完全相同。

创建报告目录后，从仓库根运行（路径按实际目录替换）：

```powershell
.\scripts\windows_deployment_probe.ps1 -RuntimeDirectory 'C:\Wenshu\runtime' -OutputFile 'C:\Wenshu\reports\before-install.json'
```

脚本不记录密钥/密码，不打开数据库，也不注册任务或修改电源策略。`runtime不存在`、`任务不存在`、`health连接失败`表示对应步骤尚未完成，不表示硬件不足。若PowerShell执行策略阻止经核对的仓库脚本，可仅在当前会话调整策略，不永久放宽系统策略。

真实旧数据先停应用及其自启动管理器，用支持完整备份的程序明确指定**原运行根和原resource**备份到全新目录；不得只复制运行中的app.db。先隔离恢复到验收目录，核对真实历史、素材、归档、导出及schema3→6/旧程序回退，再安排正式数据切换。保留唯一原件和升级后新增内容。

### 2. 建立可持续运行的团队实例

按[S6维护手册](S6-operations.md)把绿色包放在独立程序目录、runtime放在 `C:\Wenshu\runtime`，备份放在runtime数据根之外。沿用已有配置/密钥；不要用模板覆盖个人.env。启用团队模式，只在尚无管理员时初始化，创建三档真实账号并首次改密。

先以loopback手动启动，验证已登录维护人员访问`/api/ready`、人工审核和四平台导出。匿名访问ready返回401是账号规则，不代表服务不健康；只读probe也不能代替已认证ready。

停止手动实例后，在NUC具备管理员执行条件的PowerShell中注册实际任务：

```powershell
$wenshuExe='C:\Wenshu\releases\v1.1.0-rc.1\文枢.exe'
$wenshuRuntime='C:\Wenshu\runtime'
.\packaging\deployment\register_windows_task.ps1 -ExecutablePath $wenshuExe -AppDirectory (Split-Path -Parent $wenshuExe) -RuntimeDirectory $wenshuRuntime
Start-ScheduledTask -TaskName 'Wenshu-SingleInstance'
.\scripts\windows_deployment_probe.ps1 -RuntimeDirectory $wenshuRuntime -OutputFile 'C:\Wenshu\reports\after-start.json'
```

任务已存在时脚本拒绝覆盖，应先核对它的身份、程序路径和runtime。不要让手动进程和启动任务同时连接同一数据根。默认S4U/有限权限使用具备本地目录读写权的既有账号；若失败，记录Windows错误、任务事件及应用日志，再调整实际账户权限。不要把S4U对Windows网络凭据/EFS的限制直接推断为模型HTTPS请求一定不可用。

本步骤通过须同时看到：任务Running、正确端口health可达、团队已初始化、已认证ready通过，并完成一次真实账号审核/导出。任务运行中的LastTaskResult可能为267009（0x41301），不应仅因它不是0就判失败。结束当前登录会话后仍须验证可访问。

### 3. 实际维护和重启恢复

确认队列结束或可恢复、停止新操作，在NUC使用更新后的脚本：

```powershell
.\packaging\deployment\backup_windows_task.ps1 -ExecutablePath $wenshuExe -RuntimeDirectory $wenshuRuntime -BackupDirectory 'C:\Wenshu\backups\acceptance-first'
```

目标目录必须全新。脚本会恢复原先运行的任务；失败不能计为备份完成。检查清单并隔离恢复到另一目录，核对三档登录、权限、人工历史、图片和导出，然后验证原服务仍可使用。另用维护窗口由主机维护者执行重启，检查无需登录即可启动、单实例锁、队列恢复和数据一致性；不能在有任务运行时直接断电作为首个演练。

当前C盘空间足以开始小样本部署，后续风险更可能是素材、构建缓存和本机多份备份增长。建议NUC运行配置设置 `WENSHU_MIN_FREE_MB=2048`，剩余空间低于8GB时预警并核对保留策略；这是建议门槛，不是已测出的故障阈值。另一设备副本仍需落实，不能把C盘另一目录视为异地容灾。

### 4. 跨网络与持续负载

Windows绿色包是目标路线，Docker/Nginx不是验收前置；只在实际选用它们时测试相应运行方式。先确定家庭上行、路由器/NAT、私有组网方案及受保护HTTPS入口，再安排手机蜂窝和至少一名外地成员登录、图片、下载、退回/批准及SSE重连。

NUC优先有线联网，核对交流电禁止自动睡眠和BIOS来电恢复实际设置。不能仅凭Windows“从不睡眠”声称来电后一定自动开机；电源/散热/UPS情况仍未验证。

三人使用10～20个真实主题进行30～60分钟连续创作、审核和卡片导出，记录真实HTTP耗时、排队等待、模型等待、渲染时间和CPU/内存/磁盘变化，再开始3～7天试运行。只读probe的瞬时CPU值不是峰值监控，持续负载同时记录任务管理器/资源监视器数据。
试用可先以本机非模型API P95≤500ms、无500/越权/静默覆盖、可用内存不持续低于4GB为观察目标；CPU持续超过90%五分钟、磁盘响应持续变慢、频率下降或内存持续增长时定位原因。门槛可按真实基线调整，不是目前已经达标的容量承诺。正常单实例排队、外部模型等待与网络等待分别记录，不笼统认定CPU不足。

## 给部署机 Agent 的任务结束条件

明确使用当前NUC作为目标，不再等待另一台机器。先只读采集和核对授权，再完成所有当前可执行的部署、任务注册、登录/权限、离线备份/隔离恢复与本机补测；不要在代表性测试通过后自动把这些工作留给下一轮。
遇到真正需要维护者重启、管理员条件、组网/证书或真实成员的步骤时，指出具体缺项，继续完成独立工作。逐项记录“通过/失败/未执行”、命令、环境、证据、数据与回退；没有真实执行的步骤不标通过。全面验收的结束条件是本机真实部署和维护闭环通过，外部成员、手机和试运行条件也被明确落实或列为待验收。

评估Agent表现应看它是否识别设备已确认、是否推进可执行项、失败后是否定位重试、是否正确记录证据。要比较不同Agent，需在同一NUC、同一提交和同一明确任务清单下比较完成结果；当前资料不足以作能力排名。
