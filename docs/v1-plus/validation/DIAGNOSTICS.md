# 未完成验证时怎样定位原因

现有NUC报告没有资源耗尽或反复执行失败的证据，不能认定机器性能不足或Agent能力不足。下一轮按下列事实分类，允许多个原因同时存在；没有观察就写未测。

## NUC Agent 每次结束前必须交接

在本轮run的evidence中增加`handoff-<日期序号>.md`，给出已执行/失败/缺条件的case编号、当前服务/数据状态、可立即继续的项和下一步。逐项blocked要有具体所需输入、提供者别名、操作步骤/预计时段，不能笼统写“后续验证”。后台测试还在运行时记录命令、日志位置和会话状态；启动不等于完成。

记录本轮实际收到的任务范围摘要；Agent/模型版本知道就记，不知道记unknown；停止前最后一次操作、退出码/错误类别、重试结果，以及是否遇到工具拒绝、执行权限不足、上下文或会话中断。去敏后摘录与本项有关的最后回复/错误，不复制完整包含凭据的会话日志。仅“测试较慢”或“待后续”不足以评价Agent能力。

## 资源不足需要什么证据

P01/P02期间资源CSV与任务/HTTP时间线必须重叠，并写出同时运行的浏览器、Agent或其他软件。记录可用内存最小值、目标进程private bytes变化、系统CPU和磁盘队列；如发生OOM、进程被系统终止、磁盘满、SQLite busy，附当时去敏错误及进程/磁盘状态。系统CPU高但文枢进程CPU低时，先查其他负载；不要把Agent的资源消耗归到应用。

可在相同数据/负载/程序基线下关闭已确认的无关应用后复测，使用新attempt保留前后数据。温度/降频只有实际可信工具采集后才能判断，CPU型号和用时差不能直接证明热限制。无需为了诊断重装系统、购买硬件或更换数据库。

## 网络、模型与本地任务怎样分开

给一批实际任务记录接受、队列等待、开始、模型请求开始/返回、渲染开始/结束、完成时间；已有task/audit字段不足时附去敏应用日志摘要，不编造缺失时间点。队列等待不算模型执行，HTTP读取探针不代表渲染速度，外部模型429/超时与本地CPU耗时分开。

公司网受限或NUC组网不可达时记录网络类型、域名类别、超时/响应码、客户端版本、直连/中继是否实际查明；不提交公网IP/Token。相同任务能在本地完成、只跨网络失败时先定位入口/证书/代理/SSE；本地资源正常而模型请求长时间等待时先定位渠道/网络限流，不先判硬件不足。

## 权限或范围问题怎样闭环

计划任务注册被拒绝，记录实际Windows执行身份的权限类别和错误，给维护者明确的注册步骤；注销、重启、手机、外地、另一设备及自然日需要本人/成员参与时，按对应CASEBOOK安排，独立项继续执行。用户暂时不能参与的项保持blocked。

公司机复核时逐项检查证据是否覆盖标准、错误是否可重现、可执行项是否实际尝试，以及“未执行”与“执行失败”是否被混淆。发现漏做已具备条件的项，具体退回case和步骤；工具拒绝/权限问题要保留原错误。只有存在可重复的已授权任务执行轨迹，才进一步讨论执行能力；目前不作模型排名或能力结论。
