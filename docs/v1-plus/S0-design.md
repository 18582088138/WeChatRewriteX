# V1.0+ S0：实施设计与阶段边界

日期：2026-10-30。基线：`af63c6162f33de6a3834a60b168d714ea707b215`（`v1.0`，程序 `1.0.0`，schema v3）。
阶段分支：`dev/v1-plus-s0`，从 `dev/v1-plus` 创建。本文件是后续实施契约，**不代表团队功能已经实现**。
需求范围与验收以 [开发计划](../dev-plan-v1-plus.md) 为准；本轮事实与待确认信息见 [S0 验收记录](S0-acceptance.md)。

## 1. 保留的架构与实施方式

- Vue/FastAPI/SQLite 模块化单体，一个数据根、一个应用进程、一个 ASGI worker；保留现有任务线程和任务队列的所有权语义。
- `articles.id` 继续作为项目 ID，项目包含文稿及素材。新增权限表引用它，不另建一份重复的文章数据源。
- `draft_workspaces` 仍是唯一可变正文；`drafts` 的定稿记录与旧历史继续只读。版本与 `edit_revision` 双重检查继续作为写入准入。
- `reviews/review_items` 继续表示 AI/规则审稿，新增独立人工提交/评论/决定记录。`REVIEWED` 不表示人工批准。
- 导出仍由现有四个平台生成发布包，入队绑定定稿、素材与配置快照；不新增自动发布、TTS 或视频制作。
- PostgreSQL、独立 worker、实时共同编辑不进入本版必需清单。已有视频素材显示能力保留。
- 本轮不改产品版本号、不打发布标签。后续兼容功能发布可考虑 `1.1.0-rc.1`，最终按 VERSIONING 和兼容性验收确定。

## 2. 设备、部署与网络决策门槛

当前开发机类型和目标主机信息待用户确认，不能把开发机环境当作小主机条件。

S1 先提供开发机隔离数据根验证，维护者在局域网使用。部署选择按已有系统：

- 已有可维护 Linux/Docker：复用 Dockerfile，补独立持久配置、数据、日志、密钥管理与重启策略；镜像在开发机构建。
- 已有 Windows：优先现有绿色包或 Python 安装，补服务管理与开机/异常重启验证。不得假设能重装系统或已获得管理员权限。
- 代码目录与可写运行目录分离；现有源码配置路径绑定仓库、Docker 配置位于镜像内，S1 需处理持久配置而不是只挂数据卷。
- 部署访问令牌只用于旧维护模式。S2 的团队模式必须要求成员身份，包括本机请求；不得以 loopback、共享令牌或通道账号绕过成员授权。
- 先保持内网入口；S6 在获得实际设备访问后验证跨网络路径。公网 IP 不作为前提。

远程候选按顺序评估受保护私有组网、带身份控制的访问通道、条件允许时的 HTTPS 公网代理。
记录中国大陆跨城市实测、商业使用条件、手机访问、客户端安装限制、Cookie/SSE/大文件支持、维护成本。
不能承诺某个品牌免费或在成员网络可用。团队权限通过应用实现；代理不得静态公开数据根。

备份候选为另一台设备或异地存储，具体位置和密钥管理人待确认。现有 `backup_data.py` 只覆盖数据根；
S1/S6 需额外保存持久配置和必要密钥，并在新隔离目录恢复。目标 RPO ≤24 小时、人工介入后 RTO 约60分钟，均待实测。

## 3. 成员与权限规则（建议默认值，待用户确认）

一个团队；成员有管理员或普通成员身份，禁用与删除区别处理，历史责任引用不物理删除。
管理员可管理所有项目，但界面明确提示其管理访问，权限变更与例外写审计。
普通成员只有显式项目授权才可访问；团队成员身份不自动授予项目权限。

项目负责人必须是可用成员，负责项目管理、成员分配、负责人转移与归档，默认同时具有创作权限。
协作者能力用独立标志存储，可兼任：

- 只读：读取项目、文稿历史、AI 审稿、人工意见、素材、定稿、既有导出和项目费用，不能修改或发起任务。
- 创作者：具有只读能力，另可收集/上传/选择素材、编辑/AI 修复/重写/回滚、提交/撤回本人审核、定稿和导出。
- 审核者：具有只读能力，对指派给自己的人工提交评论和决定；没有创作者能力时不能修改正文或发起创作。
- 负责人：管理本项目授权、转移与归档；不能通过授权操作赋予团队管理员身份或读取系统密钥。
- 管理员：团队账号、策略、配置、日志和恢复管理；项目例外操作必须有原因，仍须检查版本冲突。

团队公共素材由管理员管理，显式共享后供启用成员读取；创作者复制到自己可写项目时保留来源。
从项目复制到公共库会扩大访问范围，只允许管理员明确执行并记录来源与审计。
成员撤权后禁止后续读取（含旧 URL/历史/SSE）和写入；已下载到成员设备的数据无法由服务撤回。
默认禁止作者自审；启用时明确提示并留痕。撤权/禁用审核者后不能继续审批，需要重新指派。
负责人停用前要求转移或由管理员接管；任何操作不得禁用最后一个可用管理员。

## 4. 数据方案与约束（拟定，S2～S5 实施）

- `teams`：单团队记录、作者自审策略、公共素材共享确认状态。与全局模型配置分开。
- `members`：稳定 ID、唯一规范化登录名、显示名、成熟密码哈希、团队角色、启用状态、会话失效版本、时间。
  禁用成员保留 ID，登录名规范化与长度规则集中校验；不记录明文密码。
- `member_sessions`：随机会话令牌的哈希、成员 ID、失效版本、到期/撤销时间及 CSRF 状态；数据库不保存原始 Cookie。
  Cookie 为 HttpOnly，HTTPS Secure，SameSite；修改请求校验 Origin/CSRF，前端开发 Origin 精确允许。
  选用成熟密码哈希库（优先 Argon2id），S2 验证目标安装与参数资源成本，锁定依赖并做冷安装验证。
- `project_access`：每个 `article_id` 一条负责人/归档/ACL revision 记录，负责人非空；`project_members` 使用
  `(article_id, member_id)` 唯一键及创作者/审核者能力。普通只读成员无写能力，所有角色变更增 ACL revision。
- `human_submissions`：项目、提交人、作者、审核者、工作版本/revision、内容摘要、不可变 `doc_json`、状态及时间。
  正文副本仅用于证据，不提供编辑接口，不生成第二份 HEAD；同项目最多一个活跃提交。
- `human_comments`：提交 ID、成员、稳定块 ID 或元信息锚点、意见、处理状态、处理人/理由/时间。
  状态为待处理/已解决/不采纳；旧快照评论可读，应用内容修改必须检查当前 HEAD。
- `human_decisions`：提交 ID、决定人、批准/退回/例外、原因和时间，不可覆盖原决定。
  定稿记录通过关联表绑定人工提交/决定和实际定稿 ID，不重写旧 `drafts.doc_json`。
- `audit_events`：成员（或明确的 legacy/system）、对象/项目、动作、结果、版本/revision、request/job ID、时间。
  成功的权限/审核/定稿/回滚/归档/导出变化和审计在同一短事务内提交；敏感失败另记脱敏日志。
- `jobs` 添加发起人、授权项目/版本与责任来源；历史发起人为空并标记 legacy，不伪造管理员操作。
  存量 `llm_calls` 按项目授权展示；全局任务/费用仅管理员汇总。
- `materials.scope=article|common`、`source_material_id`、摘要去重与归档不变；新增旧 common 共享确认边界。
  数据库文件路径不是授权身份，多行引用同一路径时必须检查可访问归属；不因同 hash 自动授权。

新增关联表使用外键、唯一约束和索引；每阶段迁移有独立版本登记。具体 schema 编号在首次实施时确定，S0 不预先升库。
权限检查在应用服务入口集中实现，写入权限、HEAD/CAS 与业务状态在同一数据库事务内复核。
外部网络调用不占用事务；返回后重新检查成员启用/权限与版本，防止撤权期间仍提交结果。

## 5. API 权限清单

以下覆盖实际基线路由；新接口在 S2/S4 实施时加入同一清单。资源 ID 先在服务器解析所属项目，
不能相信请求传入的项目 ID。无权猜测资源统一返回 404，未登录返回 401；配置禁用操作返回 403。

- 公共静态 SPA 与 `/api/health`：不含业务数据。登录/初始化仅有限公开入口；`/api/session` 在团队模式表示具体成员。
  首次管理员通过主机本地一次性初始化方式建立，远程初始化受一次性凭据保护；无公开注册。
- `/api/articles` GET：SQL 内按项目权限过滤后分页/计数/检索，不能先全量取再隐藏；POST：启用成员创建并成为负责人。
- `/api/articles/{aid}`、`draft`、`versions`、`materials`、`reviews/latest`、`review-context`、
  `publish-jobs`、`exports`、`costs`：项目读取能力，含归档与历史资料。
- `selection`、`advance`、`versions/save`、`rollback`、`reopen`、`finalize`：项目创作能力；
  所有影响正文或工作状态的修改必须携带 expected_version/revision。定稿额外验证有效人工批准及已有 AI/规则政策。
- `/api/drafts/{draft_id}/edit|regenerate|insert-refs`：从 draft ID 解析真实项目，创作能力及 HEAD/CAS 检查。
- `/api/review-items/{item_id}/resolve`：从 AI review item 解析项目，创作能力与有效版本；AI fix 属于内容修改。
- `/api/articles/{aid}/publish|publish/retry|cards`：创作能力、定稿/快照校验及任务幂等准入；读取旧导出只需读取能力。
- 项目 `materials/upload|upload-batch|url|batch-url|scan-inbox`：创作能力；共享库
  `/api/materials/upload|scan-inbox` 与 `/api/articles/imports/scan`：管理员。
- `/api/materials/{mid}/file|thumb|text`：从素材归属授权。`patch|delete|recrawl`：其项目创作能力，公共素材仅管理员。
  `copy-to-article`：来源可读且目标可写；`copy-to-common`：管理员显式共享，不能通过引用私有原路径泄露内容。
- `/files/{relative}`：复用登记/manifest/路径约束，同时核对素材、导出、旧 runs、独立卡片的项目归属。
  私有 staging、DB、备份、锁和配置仍不可读；不得仅凭 URL 或长期 URL 令牌放行。
- `/api/jobs`：成员只读授权项目任务，跨项目列表在 SQL 内过滤；无项目系统任务仅管理员。
  对成员响应不返回任务 payload 中的全量配置、绝对本机路径或内部错误细节。
- `/api/sse`：成员会话有效性与事件项目权限在发送时持续检查，撤权立即生效；系统事件只给管理员。
  心跳重新核对会话，退订清理；断线后 API 重建状态，不承诺全量事件重放。
- `/api/settings` GET/PUT、`settings/reload-env`、`logs/tail`、`ready`、OpenAPI/调试入口：管理员。
  普通成员使用单独脱敏的能力摘要（可创作/不可用原因），不通过 settings 读取全量配置或密钥。
- `materials/{mid}/reveal` 和 `articles/{aid}/exports/reveal` 会操作服务器桌面：团队模式禁用；本地维护模式才可使用。
- 新成员管理/重置密码/团队策略接口：管理员，最后管理员保护。个人登录/退出/改密只作用于本人。
- 新项目 ACL/转移/归档接口：负责人或管理员。人工提交/撤回：创作者；评论/审批：当前指派审核者；
  指派变更：负责人/管理员，撤销旧提交决定权限并留痕；例外放行：管理员、必填原因、禁止绕过 CAS。
- 新待办列表与审计读取：按当前项目权限过滤；管理员可看团队汇总。所有返回对象及关联来源也应用权限。

## 6. 人工审核、定稿与并发

人工状态独立于现有 Agent 生命周期：编辑中 → 待审核 → 退回修改/审核通过 → 定稿。
提交事务读取一致 HEAD，绑定版本、revision 和内容摘要，确认审核者当前有权限。
待审核期间允许创作者继续编辑，但内容变化会使该提交失效，需要再次提交；旧评论/决定仍可查看。
审批事务核对当前指派、启用状态、自审策略、提交状态、当前 HEAD；不能批准过期提交并推进新正文。

正文、标题、图片/引用、来源等成品相关变更使人工批准失效，回滚也需重新审批；评论处理状态变化不影响批准。
复用 `draft_service.content_hash`，S4 确认其覆盖成品内容；外部素材 recrawl 不原地替换历史素材，
影响被引用素材的元信息修改需纳入成品摘要或触发复核，不能只比较正文字符串。
定稿同时检查当前有效人工决定、HEAD/CAS 和已有规则/AI 审稿策略，增加 revision 保留旧请求保护。
管理员例外只替代可例外的审核门槛，仍绑定明确快照和原因，不能越过并发冲突。
导出继续冻结已定稿内容；人工决定变更或后续编辑不会改写已排队快照。

编辑占用提示仅辅助 UI，CAS 才是提交裁决。若引入租约，按成员/项目/到期时间管理，失联自动释放；
保存冲突保留本地输入，提供复制、比较及重新应用路径，不自动覆盖。
重复提交/批准/导出使用幂等键及唯一约束；同一键不同请求内容返回冲突。
任务入队、认领、恢复和结果提交均复核成员权限；排队任务撤权后标记取消/失败及原因，
已发出外部请求按现有能力结束但禁止无权结果写入，不承诺强制取消或恰好一次执行。

## 7. 旧数据迁移与回退

1. S0 不读取真实业务正文、不启动真实数据根、不改 schema。S1 准备独立验证根，真实升级前停止服务、完整离线备份。
2. S2 新增身份和授权基础。尚未初始化管理员时，团队模式不开放业务访问，也不认领旧待处理任务。
3. 初始化管理员后，事务内为旧项目建立管理员负责人/私有访问记录；不改变旧文章 ID、目录或素材路径。
   旧项目只有管理员可见，协作者由管理员/负责人显式分配。自动目录导入也默认管理员私有。
4. 旧 common 库默认仅管理员可读。管理员确认分享后开放选定素材；若采用逐条共享标志，不能由一个全库开关误开放。
5. `draft_changes`、旧工作文稿、历史定稿、导出 manifest、归档素材和来源关联保留。
   来源项目不对成员开放时，复制结果可读，但来源私有对象的详情/URL不可泄露。
6. 旧 AI 审稿按既有匹配/失效规则读取，不迁移为人工批准。旧定稿可读和下载既有包；
   新定稿、新生成或重新导出旧定稿前须补人工审核/明确管理员例外记录，不能因旧状态直接通过新门槛。
7. 旧 pending/running 任务不伪造发起人。升级停机窗口由管理员确认暂停、取消或恢复；
   确认恢复时另记责任承接和当前授权，running 任务只在取得 OS 锁后按既有恢复语义重试。
8. 迁移事务与 `schema_migrations`/`user_version` 同步提交，唯一键与固定初始团队 ID 保证重复启动幂等。
   现有 `init_db` 每次写 `user_version=3`，S2 必须先改为逐版本迁移，禁止降号或识别不了的高版本库继续写入。
9. 迁移失败停止启动，不开放半迁移数据；自动数据库副本不能代替完整备份。先在隔离旧库验证重复启动和故障恢复。
10. 回退停止新服务，保留升级后新增编辑/导出，使用旧程序与对应完整备份在独立根恢复核验后切换。
    禁止把新增 schema 的唯一库直接交给旧 `1.0.0` 写入；切 Git 分支不恢复用户数据。

## 8. 后续阶段清单与验收门禁

- S1：持久配置与目录分离、服务管理材料、单实例/ready、隔离流程/重启/离线备份；真实主机另标状态。

- S3：项目授权管理、公共素材确认、旧库幂等迁移、文件/SSE/检索隔离、任务责任与撤权。
- S4：不可变人工提交、意见/决定、版本绑定、定稿门槛、导出对应批准与浏览器退回修订闭环。
- S5：编辑提示和冲突恢复、并发撤权、迟到 AI、幂等请求、审计与站内工作列表。
- S6：获得真实设备后完成跨网络和手机、代理/自动重启、另一设备备份、隔离恢复时间测量。
- S7：10～20 个代表主题、实际人数负载、3～7 天试运行、回归与版本材料；未完成远程验收不可宣布最终交付。

每阶段记录实现、等价环境、真实小主机、外地成员四类状态，以及证据、数据变化、遗留项和回退。
